# 输入与输出约定

本页将最初讨论中的数据内容整理为具体文件约定。原讨论已经给出 GT 的 `entities`、`required_variables`、`structure`，以及模型输出的 `dimensions`；以下目录和文件名是本次落实这些内容的约定，并非声称原讨论已逐字确定全部路径。

## 1 单个案例

```text
cases/<case_id>/
├── case.json                 案例清单、单位、文件哈希与就绪状态
├── input/
│   └── model.step            唯一提供给模型的案例文件
├── gt/
│   └── gt.json               特征、必要变量、结构关系及参考值
└── sources/
    └── ...                   原始 SLDPRT 与 STEP 版本及来源层级
```

这是案例完成配对与 GT 提取后的目标结构。当前六例仍处于 `source_collected`：只有 `case.json` 和 `sources/`，尚未生成 `input/` 与 `gt/`。不得用空 JSON 或臆造参数把它们伪装成可评分案例。正式生成时需同步升级源文件校验器与案例清单版本。

`input/` 是模型可见边界；`gt/`、`sources/` 和带来源信息的内部清单均不挂载给模型。SLDPRT 特征树或等价 CQ 建模程序用于后台生成 GT，无需配套工程图。若采用 CQ 来源，应同时扩展当前只接收 STEP／SLDPRT 的源文件合同。

## 2 GT 内容

提取过程分为两层：原始提取结果保存支持范围内的特征、草图、尺寸和约束；评分 GT 只保留确定最终几何所需的特征、独立变量和结构关系。

| 字段 | 内容 |
| --- | --- |
| `case_id` | 与输入 STEP 对应的案例标识 |
| `units`、`geometry` | 单位、坐标约定和固定基准 |
| `entities` | 特征类型、几何引用、位置及尺寸参数 |
| `required_variables` | 必须由图纸信息确定的连续量 |
| `structure` | 通孔／盲孔、数量、阵列、对称等离散或结构要求 |

评分 GT 不规定必须标“左边 20”还是“右边 30”。它规定需要确定哪个几何量，并保留三维真值用于核验。

单案例保存为 `gt/gt.json`；批处理可把各案例对象逐行汇总成 `gt.jsonl`，每个案例一行。JSONL 是导出的汇总视图，不另行手工维护第二份答案。

## 3 模型提交

提交位于每次运行的工作目录，与案例数据分开：

```text
submission/
├── drawing.pdf              本次生成的二维图纸
├── prediction.json          特征、视图、尺寸与结构标注
└── model.py                 可选的 CQ 特征构造表示
```

这里的 `drawing.pdf` 是模型输出，不是要求下载或提供的配套参考图。CQ 可代替特征构造表示，但不能代替二维制图结果和尺寸关系记录；最终仍需通过适配器得到统一的可评分结构。

`prediction.json` 至少包含：

- `features`：模型识别的特征、参数、几何引用与关系。
- `views`：视图方向、剖切定义及视图 ID。
- `dimensions`：每个标注的 ID、所属视图、类型、轴向、起止实体或参数，以及 CAD 工具记录的数值。
- `structure`：图纸实际表达的贯穿、数量、阵列等信息。

二维线到三维边、面的对应由 CAD 制图工具记录。AI 选择已有几何引用和标注关系，无需额外猜测每条投影线属于哪个三维面。通用面、边引用不应提前泄漏隐藏的特征类别与 GT 参数清单。

CAD 工具在同一次标注操作中计算数值、绘制尺寸并记录关系。受信工具已经保证数值与实体绑定时，第一版重点评价关系是否完整与独立，无需用 OCR 重读一遍数字。模型自行填写的 JSON 不具有这种保证，必须与工具日志和实际图纸对应后才能入图。

## 4 可参考的示例

[尺寸链示例](../examples/dimension_chain/README.md) 提供具体 `gt.json`、`prediction.json` 和人工核算的 `expected.json`，演示“左距 20”与“总长 50 加右距 30”的等价性。
