# BenchCAD 3D→2D：SolidWorks＋Codex CLI 版本的 AI 如何工作

本地讨论稿 · 更新于 2026-10-16 · 以 Case 13 实际代码为准。

适用范围：本地 Windows、SOLIDWORKS 2023、Codex CLI 0.163.0 的 Case 13 试验。本文不是 BenchCAD 2.0 的运行说明，也不代表 FreeCAD 后端或自建 API Agent 已实现。

**公开阅读版：文中的脚本名指本地试验代码，本次尚未迁移为仓库可运行入口。**

**先看第 1 节即可理解整体。后面按“输入、工具、循环、反馈、提交、限制”逐项展开。**

标记含义：**已实现**是当前程序已有的行为；**待验收**是还没有完整证明可靠；**建议**是尚未实施的设计。

## 1. 一眼看懂：谁负责什么，两次 AI 任务

**我们的 Python 控制程序管理任务；Codex CLI 管理模型与工具之间的循环。SOLIDWORKS 执行 CAD 操作，评测器最后检查结果。**

```text
我们的控制程序
  │ 准备 STEP、任务说明、工具、权限和预算
  ▼
Codex CLI：出图任务（新会话）
  模型决定操作 → 工具执行 → 结果返回模型 → 再决定操作
  例如：读 STEP → 创建视图 → 标注 → 看图 → 修改
  │ 出图 AI 调用工具保存原生工程图，写提交标记，然后结束
  ▼
控制程序：复制并重开提交的工程图 → 调用 SOLIDWORKS 导出最终 DXF
  │ 控制程序读取同一工程图生成 JSON，并调用渲染脚本把最终 DXF 转为 PNG
  │ 控制程序只把最终 DXF 和该 PNG 交给重建 AI
  ▼
Codex CLI：重建任务（另一个新会话）
  读图 → 建模 → 自查 → 修改 → 提交 STEP
  ▼
评测器：读取原 STEP 和重建 STEP，计算 IoU
  │ 本次缺批准的剖切 GT，评测器未计算剖切分数
  │
  └─ 分数写入报告，不返回给本轮两个 AI
```

| 角色 | 它决定什么 | 它不负责什么 |
|---|---|---|
| BenchCAD 控制程序 | 发任务、文件边界、时间资源、提交处理、日志、评分 | 不替被测 AI 选择剖面或补尺寸 |
| Codex CLI 内的模型 | 怎样理解零件、用哪些工具、怎样出图、何时结束 | 无权决定自己的 GT 分数 |
| CLI 执行系统 | 发起模型请求、执行工具、返回反馈、维护上下文 | 不保证模型的设计判断正确 |
| CAD 程序 | 按命令建立视图、剖切、尺寸和文件 | 不自动知道我们要求表达哪些特征 |

当前模型接口是 Codex CLI；当前出图 CAD 后端是 SOLIDWORKS。二者可以分别替换，不是绑定在一起的一件东西。

本文中，**出图 AI** 指执行出图任务的被测模型；**重建 AI** 指另一个新会话中的重建模型；**控制程序** 指我们编写的固定 Python 程序。AI 决定绘图操作并请求调用工具，实际的文件读写、CAD 操作和渲染由工具执行。

## 2. 输入：AI 一开始拿到什么

**出图 AI 可以直接读取 STEP，并自行写代码计算几何。当前没有默认附送六视图，也没有把 STEP 文件全文直接塞进提示词。**

| 任务开始前，控制程序准备的输入 | 出图 AI 能读取什么 | 重建 AI 能读取什么 |
|---|---|---|
| 任务说明 | 出图目标、工具说明位置、预算和提交方式 | 重建目标、工具位置、预算和提交方式 |
| 原 STEP | 可读，`input/model.step` | 不可读 |
| 原生几何缓存 | 可用，`work/input-cache.SLDPRT` | 不提供 |
| 最终 DXF | 出图任务开始时不存在；不是出图 AI 的输入 | 控制程序从提交的原生工程图导出，再复制为 `input/drawing.dxf` |
| 最终 DXF 的预览 PNG | 出图任务开始时不存在；不是出图 AI 的输入 | 控制程序渲染最终 DXF，再复制为 `input/preview.png`；重建 AI 调用看图工具打开 |
| 专家图纸、GT JSON、评测日志 | 不提供 | 不提供 |

**出图过程中使用的自查文件，与提交后用于评测的文件，生成阶段不同：**

| 文件 | 谁发起生成 | 哪个程序实际生成 | 生成时间与用途 |
|---|---|---|---|
| 自查 DXF：`drawing/output/drawing.dxf` | 出图 AI | AI 编写的脚本调用 SOLIDWORKS 导出 | 出图任务进行中；供出图 AI 检查和修改 |
| 自查 PNG：路径由出图 AI 指定 | 出图 AI | `render_dxf.py` 渲染自查 DXF | 出图任务进行中；出图 AI 再调用看图工具查看 |
| 最终 DXF：`drawing/output/frozen/drawing.dxf` | 控制程序 | `finalize_drawing.py` 调用 SOLIDWORKS 导出 | 出图 CLI 结束并通过提交状态检查后；用于后续评测和重建 |
| 最终 PNG：`drawing/output/frozen/preview.png` | 控制程序 | `render_dxf.py` 渲染最终 DXF | 最终导出成功后；作为重建 AI 的图片输入 |
| 图纸结构 JSON：`drawing/output/frozen/drawing.json` | 控制程序 | `finalize_drawing.py` 调用 CAD 状态提取函数 | 与最终 DXF 来自同一份原生工程图；供控制程序和评测器使用 |

控制程序没有直接把出图 AI 的自查 DXF 当作最终 DXF。两份文件可能内容相同，但必须区分生成来源和用途；当前重建流程使用 `frozen/` 中的导出结果。

上述路径以本试验根目录为起点。当前最终提交流程没有生成 PDF；模板目录中已有的 PDF 只是模板展示文件。

原生缓存由同一个 STEP 转换而来，用来绕过当前受限账户下的 STEP 导入问题。它不提供专家视图或标注；本轮输入条件必须写成“STEP＋中性原生缓存”。

控制程序通过标准输入 stdin 把任务说明送入 CLI。控制程序把 STEP 等输入放在对应任务目录里，模型通过工具读取；提供文件路径不等于模型已经看过文件内容。

**观察策略：**不另设一套“只能查询六视图”的服务。AI 可以读取几何、创建任意可实现的视图、渲染自己的图纸，并重新渲染局部区域；每次操作消耗同一任务的时间预算。

## 3. 工具：AI 究竟能做哪些操作

**模型先通过 CLI 的通用工具读写文件、执行命令、查看图片，再通过 Python 调用 CAD。我们提供常用 CAD 帮助函数，但目前没有把 CAD 能力限制成一个封闭的函数菜单。**

### 3.1 CLI 这一层

| 能力 | 模型提供什么 | 模型得到什么 |
|---|---|---|
| 执行命令 | 命令、工作目录等参数 | 标准输出、错误输出、退出状态；长任务可能先返回运行状态 |
| 读写代码和文件 | 文件路径、代码或修改内容 | 文件内容或修改成功／失败信息 |
| 查看图片 | 已生成的图片路径 | 图片作为视觉输入，而不只是路径文字 |

这些能力由 CLI 提供。当前不是我们自己实现了一个只接受 Python 代码块的解析器。

模型可以执行 Python，也能执行权限允许的其他命令。个人记忆、插件、应用、多智能体和网页搜索被配置关闭；这不等于全部访问路径都已完成隔离验收。

### 3.2 当前提供的 CAD 和绘图工具

下表列的是本轮核心入口。模型还能阅读允许目录中的库代码，并调用底层 SOLIDWORKS API。

| 工具／函数 | 用途 | 输入和输出 | 当前边界 |
|---|---|---|---|
| CadQuery / OCP | 读取 STEP、计算几何、建立或导出实体 | STEP／Python 参数 → 几何对象、数值或文件 | 数值只来自可访问的几何；不是专家答案 |
| ezdxf | 读取、分析或编写 DXF | DXF／Python 参数 → 图元、数值或 DXF 文件 | 手工画的线条不一定对应原生 CAD 视图 |
| `cad_exec.py` | 把 CAD Python 脚本交给受限工作进程 | `work/` 内脚本路径与参数 → 日志、错误和退出码 | CAD 调用串行，单次执行上限 300 秒 |
| `PilotSession` | 创建和清理本任务的 SOLIDWORKS 会话 | 会话内执行 CAD 操作 → CAD 对象 | 核查不复用已有会话，并纳入资源预算 |
| `s.open` / `s.save` | 打开或保存原生 CAD 文件 | 路径与 CAD 文档 → 文档对象或磁盘文件 | 每次 CAD 调用结束前要保存 |
| `NewDocument`＋空白模板 | 创建图纸 | 模板、纸张尺寸 → 原生工程图 | 模型选择第一角法或第三角法模板 |
| `CreateDrawViewFromModelView3` | 创建模型关联视图 | 模型路径、方向、纸面位置 → 视图对象 | 前、后、顶、底、左右、等轴测等方向由模型选择 |
| `model_view_name` | 解析视图名称 | 模型、方向名 → 本机对应名称 | 处理部分中英文名称差异 |
| `fit_view` | 把视图放进指定区域 | 视图、区域位置与尺寸 → 调整后的视图 | 不替模型决定应该需要几个视图 |
| `drawing_helpers.section` | 创建原生直线全剖视图 | 母视图、切线位置、水平／竖直方向、翻向、目标位置 → 剖视对象 | 当前通用封装覆盖直线全剖，不代表所有复杂剖法已支持 |
| `Annotations.circle/edge/vertex/vertex_at` | 找到要标注的模型实体 | 坐标、半径等 → 对应边或顶点；找不到时报错 | 不是让模型凭空写一个尺寸数值 |
| `Annotations.dim` | 创建几何关联尺寸 | 实体、尺寸类型、纸面位置、预期值 → 原生尺寸对象或错误 | 支持直径、半径、水平、竖直、对齐尺寸 |
| `Annotations.note` | 创建附着于边的引线注释 | 边、文字、纸面位置 → 注释对象或错误 | 检查附着；不保证注释文字的工程含义正确 |
| `add_note` / `style_dimension` | 添加普通文字／设置尺寸样式 | 文字、位置或尺寸对象 → 注释或样式修改 | 普通文字可能写错，需另行验证 |
| `export_dxf` | 导出当前图纸 | 原生文档、路径 → DXF 文件 | 导出成功不代表工程表达完整 |
| `render_dxf.py` | 生成图纸预览 | DXF、输出路径、可选 layout 和 bbox → PNG 及来源信息 JSON | 局部放大是重新渲染选定范围；模型还须调用看图工具 |
| 原生 SOLIDWORKS API | 补充帮助函数没有覆盖的操作 | AI 编写的 API 调用 → 对象、数值或错误 | 能尝试半剖／详图等功能，但当前没有全部验证通过 |

`Annotations.dim` 的“预期值”由 AI 自己提供。函数比较 CAD 实测值和该值；它不读取 GT，也不代表尺寸已通过专家规范审查。

**当前工具不是技能自动注入。**任务说明让模型阅读 `tools/TOOLS.md`，再自行查看函数签名。脚本被放进共享只读工具目录；个人 skill 注入被关闭。

`check_dxf.py` 也在共享工具目录，AI 可以运行它检查自己的 DXF。它只报告近似文字包围盒重叠候选，不返回隐藏评分，也不是完整碰撞验收。

## 4. 循环：为什么发一次任务就能一直工作

**控制程序只启动一次 CLI，并把任务说明发给它。后面的多次模型请求和工具反馈，由 CLI 内部循环组织。**

概念流程如下，不是本项目重写的 Codex 源码：

```text
CLI 把任务、工具定义和当前上下文送给模型
  ↓
模型返回“工具调用”还是“最终答复”？
  ├─ 工具调用 → CLI 检查权限 → 执行 → 把结果加入上下文
  │                                         │
  │                 再请求模型 ←─────────────┘
  └─ 最终答复 → 结束本次 CLI 任务

同时，外部控制程序检查超时、取消和日志上限；必要时终止任务进程。
```

例如，模型要求执行 `make_views.py`，脚本返回“视图创建失败”。CLI 把错误送回模型，模型可以修改脚本再运行；没有人需要手工复制这段错误。

模型收到的是此前对话及工具结果构成的上下文。长任务可能涉及 CLI 的上下文管理；不能承诺每次请求都带着全部原始日志。

本项目的调用关系是：

```text
runner.py → run_episode.py → codex exec → 模型与工具循环
                 │
                 └─ pilotlib.py：启动进程、预算和看门狗
```

手工执行一次 `codex exec` 也能开始循环。我们用脚本包装它，是为了固定任务配置、记录结果，并在外部落实预算；单独的一条普通命令不会自动拥有全部 BenchCAD 规则。

## 5. 反馈：每次操作后，AI 实际看到什么

**操作反馈告诉 AI“刚才做成了什么、哪里报错”。它不告诉 AI“和标准答案相比得了多少分”。**

| 刚才的操作 | 反馈内容 | 会自动得到图片吗 |
|---|---|---|
| 执行几何计算 | 脚本打印的坐标、尺寸、统计或错误 | 不会 |
| 创建／修改 CAD | 打印日志、异常、退出状态；已保存的文件 | 不会，需另外渲染并打开 |
| 渲染 DXF | PNG 文件、路径、来源哈希等 | 仅生成文件；再调用看图工具才得到视觉输入 |
| 查看 PNG | 整图或局部图像 | 会 |
| 自查重叠 | 近似候选数量和位置 | 不会自动变成扣分 |
| 写提交标记 | 普通文件写入结果 | 当前不会立刻返回“收卷成功”或 IoU |

CAD 工作进程的响应包含 `exit_code`、`timed_out`、`elapsed_seconds`、`stdout`、`stderr`、`infrastructure_error`。正常命令包装器主要转发 stdout、stderr 和退出码；完整响应也保存在任务目录。

每段 stdout／stderr 最多向任务响应保留末尾 200,000 个字符。更完整的运行证据由控制程序另存，不能说模型每次都看到完整历史日志。

## 6. “30 轮”到底是什么意思

**当前没有 30 轮硬上限，也没有每一轮提交图纸再评分的流程。先定义计数单位，才能实施这个规则。**

| 名称 | 一次指什么 | 当前能否直接作为“30 轮” |
|---|---|---|
| CLI 启动 | 完整启动一个出图或重建任务 | 不能；一次启动里可以做很多操作 |
| CLI 的 `turn` | 对一次用户任务的处理过程 | 不能当成一次内部模型请求；本次一个 turn 含很多工具操作 |
| 模型决策轮 | 模型产生一次响应，可能含多个工具调用 | 当前没有可靠计数和在第 30 次前阻断的实现 |
| 工具调用 | 调用一次执行、读图等工具 | 当前有部分事件记录，没有统一硬上限 |
| CAD 请求 | 交给工作进程执行一次 CAD 脚本 | 可从队列明确计数，但一段脚本可含很多 CAD 操作 |
| 最终提交 | 交出本次任务的最终文件 | 当前每个阶段收一个最终结果 |

**若以后定义 30 个模型决策轮：**每轮可以请求读文件、执行脚本、看图片，或宣布结束；工具执行结果作为下一轮上下文。最终提交只占其中一次，不是允许提交 30 次来试探分数。

一个模型响应调用多个工具，按“模型决策轮”记为一轮；按“工具调用次数”则分别计数。长命令的轮询也需要统一规则，不能让不同 CLI 的包装方式改变排名。

**建议：**当前先使用统一总时间预算，并报告工具调用和 CAD 请求次数。若要研究 30 轮预算，再接入能可靠拦截对应事件的控制层；仅在提示词写“最多 30 轮”不算实现。

## 7. 提交：交什么，谁来接收

**当前 AI 通过写文件请求提交，控制程序在 CLI 退出后读取并处理。聊天里说“完成了”不算提交，写标记也不等于文件已经验收。**

| 阶段 | AI 生成的文件 | 提交标记 | 控制程序后续操作 |
|---|---|---|---|
| 出图 | 出图 AI 调用 CAD 工具保存 `output/drawing.SLDDRW`，并导出供自查的 DXF | 出图 AI 写入 `output/SUBMIT.json`，内容为 `{"native":"drawing.SLDDRW"}` | 控制程序重开提交的原生图纸，调用 SOLIDWORKS 导出最终 DXF，提取 JSON，再调用渲染脚本生成 PNG |
| 重建 | 重建 AI 调用建模工具保存 `output/model.step`；有歧义时另写 assumptions | 重建 AI 写入 `output/SUBMIT.json`，内容为 `{"step":"model.step"}` | 控制程序检查提交路径；评测器读取原 STEP 与重建 STEP，计算 IoU |

`SUBMIT.json` 是 AI 写的很小的“交卷单”。`drawing.json` 是控制程序读取 CAD 状态生成的“图纸结构记录”；两者不是同一个 JSON。

当前写标记后应由 AI 结束任务。控制程序没有在标记首次出现的瞬间锁住文件；如果需要严格“一经提交立即封卷”，需要新增受控提交接口。现在不能把提示词要求当成这种接口已经存在。

当前控制器会区分：提交请求、没有提交、超时、基础设施失败、取消。之后还会检查文件是否能导出、是否非空、哈希是否匹配等；CLI 退出码为 0 本身不证明图纸合格。

## 8. JSON 和评分：哪些东西不会反馈给 AI

**图纸结构 JSON 来自最终原生图纸，不是从 AI 的自述推断。重建 AI 只拿 DXF 和 PNG，不拿这个 JSON、原 STEP 或专家资料。**

| 数据／结果 | 谁生成 | 用途和现状 |
|---|---|---|
| `drawing.json` | 控制程序调用 CAD API | 记录视图、变换、剖切和哈希；复杂剖切未全部支持 |
| GT JSON | 专家标注流程 | 规定需要的剖切；本次 Case 13 尚缺批准的 GT |
| IoU | 独立评测器 | 模型各自居中、等比例归一化；分别搜索原候选与镜像候选的 24 个正交旋转，采用较高值；镜像更高时同时报告两值并标记 |
| 重叠候选 | 检查脚本 | 目前不是完整碰撞扣分 |
| token、时间、费用 | 控制程序汇总日志 | 费用为带假设的 API 折算，实际订阅扣费未知 |

**暂缓专家图纸重建校正：**当前不执行“专家 DXF → AI 重建 STEP”来计算基准分母，也不将本次 IoU 除以专家重建 IoU。AI 所画 DXF 的独立重建评测保留。镜像规则及近期决定见[近期讨论记录](DECISIONS.md)。

原生图纸是当前可靠提取视图语义的依据。若 AI 只用 ezdxf 手工画线，或只交一个 DXF，就不能保证现有脚本恢复全部剖切语义；当前出图协议因此要求原生图纸。

## 9. 严格执行：哪些靠程序，哪些还靠模型配合

**CLI 能执行配置的权限规则，但不能保证模型总画对、总按时提交。需要严格的实验规则，就必须在控制程序或工具入口检查它。**

| 规则 | 当前怎么落实 | 状态 |
|---|---|---|
| 总时间 | 每个 AI 阶段 60 分钟，外部看门狗超时终止 | 已实现；轮询有小幅延迟 |
| CAD 单次时间 | 工作进程执行最多 300 秒；排队和等待计入阶段总时间 | 已实现 |
| 内存与 CPU | Windows Job 管理已归入的进程；4 GiB 聚合提交内存、50% CPU 配额 | 已实现；不是固定 4 个核心，也不是模型服务器的资源限制 |
| 文件边界 | 输入只读，任务目录可写，共享工具只读，控制器和评测目录拒绝访问 | 部分路径已验证；图片等访问入口仍待完整验收 |
| 网络 | 被测工具的网络被配置禁用；CLI 仍需联网请求模型 | 已配置；不能称整台电脑离线 |
| 记忆与其他 Agent | 新会话，忽略个人配置，关闭记忆／插件／多智能体 | 已配置；不等于模型没有训练知识 |
| 正确投影法、标注完整 | 提示词要求＋后续检查 | 模型可能违反；相关完整验收未完成 |
| 30 轮限制 | 当前没有执行该限制的代码 | 未实现 |
| 提交即锁定 | 当前等 CLI 退出后再处理提交 | 未实现即时锁定 |

配置文件里的 `max_repair_cycles=3` 目前没有被运行循环消费，不能据此声称有“三轮修复限制”。模型可以在总预算内多次修改自己的图纸。

当前试验可继续验证流程；完整隔离验收、剖切 GT、碰撞扣分和复杂视图适配仍有缺项。

## 10. 仓库：已经确定一个仓库、两个后端

SolidWorks 和 FreeCAD 共用任务、记录和评测规则，分别维护 CAD 工具、环境和原生状态提取。具体目录和迁移状态见 [架构说明](ARCHITECTURE.md)。FreeCAD 尚未完成本项目端到端验收。
